# PRD Builder

**一个面向 AI Agent 的自适应、低 Token 消耗 PRD 生成 Skill。**

PRD Builder 帮助 AI 编码 Agent 将产品想法转化为结构化、可执行的产品需求文档（PRD），避免所有任务都走同一套复杂、耗时的工作流。

它会根据任务复杂度调整需求分析流程：简单任务采用轻量模式，具有明显权衡和依赖的功能采用标准模式，大型项目则使用多角色协作流程。

**核心目标：把 Token 花在真正影响需求质量的地方，而不是不必要的流程开销上。**

## 为什么需要 PRD Builder？

在 AI 辅助产品开发中，需求分析本身也可能变得昂贵。

一个简单的需求变更，可能触发大量上下文加载、多轮审查、并行 Agent 协作，以及一系列不必要的文档生成。对于复杂项目，这些步骤可能很有价值；但对于简单任务，它们也会带来额外的 Token 消耗和执行时间。

PRD Builder 尝试解决这个问题：

- **自适应复杂度**：根据任务范围、状态变化、风险、协作需求和长期维护影响选择工作流。
- **按需加载上下文**：只读取当前任务真正需要的指令、参考资料和项目材料。
- **控制流程开销**：简单任务不必承担大型项目的流程成本，同时保留必要的需求质量检查。
- **面向现有项目**：考虑已有规范、依赖关系、权限、边界条件和实现约束。
- **支持任务续接**：通过精简的工作快照保留关键决策和未解决事项，避免反复重建完整上下文。



## 工作模式

PRD Builder 提供三种工作模式。


| 模式               | 适用场景                | 工作方式                   |
| ---------------- | ------------------- | ---------------------- |
| **Lite（轻量）**     | 小功能、简单变更、局部修改       | 最少化上下文加载，主要输出一份 PRD    |
| **Standard（标准）** | 涉及状态变化、权限或重要方案权衡的功能 | 增加需求分析，并在必要时澄清关键问题     |
| **Project（项目）**  | 大型、跨页面或涉及多个模块的项目    | 使用多角色协作、结构化审查和更完整的项目文档 |


Skill 会根据任务复杂度选择初始模式。如果分析过程中发现额外风险或依赖，也可以升级到更严格的工作流。

目标不是让每份 PRD 都更短，而是避免在简单任务上支付大型需求分析流程的成本。

## Token 优化效果

我们使用相同的模型、虚构项目材料和任务提示词，对重构前后的版本进行了对比测试。两组测试唯一的主要变量是 Skill 版本。

### 测试结果


| 任务规模 | 输入 Token 变化 | 输出 Token 变化 | 执行时间变化 |
| ---- | ----------- | ----------- | ------ |
| 小型任务 | −89%        | −83%        | −80%   |
| 中型任务 | −81%        | −63%        | −56%   |
| 大型任务 | −20%        | −7%         | −12%   |


*以上数据来自每种任务规模各一次的测试，属于初步结果，不代表所有模型、项目或 Agent 环境下的普遍表现。*

简单任务的收益最大，因为旧版工作流默认加载了较多文件，并生成了许多并非每次都需要的产物。

大型任务的优化幅度较小，因为它们仍然需要大量上下文、协作和文档。

### 主要优化

- 从默认的重型工作流调整为三种按复杂度选择的模式。
- 将主入口 `SKILL.md` 从约 18.7 KB 精简到约 12.9 KB。
- 将参考资料改为按需加载，而不是默认广泛读取。
- 将项目专属规范集中到统一来源，减少重复定义。
- 将工作日志调整为精简快照，并通过增量记录追踪变化。
- 将默认值变更的回归影响，以及批量操作的幂等性和服务端校验纳入质量检查。

这些调整同时针对 Token 消耗和执行开销，并尽可能保留对实现质量真正重要的检查。

## 不只关注 Token，也关注质量

降低 Token 消耗只有在 PRD 仍然具有可执行性的前提下才有意义。

对测试产物进行的初步盲评结果如下：


| 任务规模 | 旧版评分   | 新版评分   |
| ---- | ------ | ------ |
| 小型任务 | 8.5/10 | 8/10   |
| 中型任务 | 6.5/10 | 8.5/10 |
| 大型任务 | 6/10   | 9/10   |


小型任务的结果也提醒我们：更轻量的工作流可能遗漏某些细节。测试中发现了默认值变更的回归影响等问题，随后将相关检查补充进了质量清单。

这些评分仅用于初步参考。每种任务规模只测试了一次，评审评分也存在波动，因此还需要更多真实场景验证其稳定性。

## 安装

克隆仓库：

```
git clone https://github.com/leonardwwq/prd-builder-skill.git
```

如果你的 Agent 环境使用 `~/.dsh/skills/` 作为 Skill 目录，可以参考以下安装方式：

```
mkdir -p ~/.dsh/skills
cp -R prd-builder-skill ~/.dsh/skills/prd-builder
```

其他 Agent 平台请根据其 Skill 加载规范调整安装路径。如果仓库中的 Skill 位于独立子目录，应复制该目录，而不是整个仓库。

## 使用方式

安装并确保 Agent 能够识别该 Skill 后，直接描述需要整理的产品需求即可。

**简单变更**

```
使用 PRD Builder，为广告活动列表新增一个筛选条件编写 PRD。
控制需求范围，并考虑现有功能的行为。
```

**涉及方案权衡的功能**

```
使用 PRD Builder，为广告组设计批量编辑功能。
明确权限边界、校验规则、失败处理，以及对现有工作流的影响。
```

**大型项目**

```
使用 PRD Builder，规划一个涉及广告活动配置、报表和共享数据模型的多页面功能。
识别跨页面依赖，并在最终输出前检查需求之间是否存在矛盾。
```

Agent 应根据任务复杂度选择合适的工作模式，并生成对应的 PRD 产物。

## 设计原则

1. **复杂度决定流程**：简单任务不应该承担大型项目的流程开销。
2. **上下文也是成本**：参考资料应该在相关时加载，而不是因为存在就全部读取。
3. **质量检查要有重点**：优先检查可能导致实现错误的问题，避免重复的流程性工作。
4. **进度应该可以续接**：保留决策和未解决事项，不必每次携带完整历史。
5. **用实际结果衡量优化**：同时关注 Token 消耗、执行时间、需求遗漏和返工，而不是只追求更低的 Token 数量。



## 局限性

- Token 节省幅度取决于任务复杂度、模型行为、Agent 实现方式，以及上下文缓存和计费规则。
- 复杂项目仍然需要大量分析、协作和文档工作。
- 当前测试结果属于初步验证，不能视为普遍适用的性能保证。
- 本 Skill 辅助需求分析与文档生成，不保证生成的需求完全正确，也不保证后续代码达到生产环境要求。



## 后续改进方向

- 在更多真实需求中验证效果。
- 补充现有项目局部修改场景的回归测试。
- 使用更多独立样本评估需求质量。
- 更准确地衡量实际计费成本、执行时间和下游返工。
