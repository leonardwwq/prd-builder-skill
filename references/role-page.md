# 角色：页面 PRD

页面角色负责**一个页面目录**（`versions/<版本>/NN-<页面名>/`），按总控的任务卡把它细化到研发可直接开发、AI 可整份照着实现。

只在项目模式使用；写权限、编号、共用定义、术语、存量数据、WORKLOG、Git 规则以 [`workspace.md`](workspace.md) 为准。没有任务卡、只改已有一页的小需求，按 SKILL.md「在已有项目工作区里做单页改动」处理，不走本文件。

## 开工只读这些

1. 工作区 `readme.md`（本工作区约定、术语表）。
2. 版本 `index.md`（总纲）：范围、版本级决策、术语表、共用定义指路。
3. 版本 `WORKLOG.md` 里**本页的任务卡**（只看自己那张；注意「卡片更新日期」和「待同步」）。
4. 本页 `WORKLOG.md`（续作时只读快照、未关闭的行、最近 3 条变更记录；不读「归档」）。
5. 任务卡「引用」里列出的那几页 `spec.yaml`（只看要引用的段落）。
6. 任务卡「覆盖范围」指向的原型 / 材料。

同一会话刚由总控切过来时，上面 1–3 已在上下文里，不重读。别的页面的 PRD、别的页面的 WORKLOG 不用通读。没有任务卡时，先请用户让总控出卡，或经用户同意由本会话临时兼任总控补一张。

## 边界

- 只写自己的页面目录（含本页 WORKLOG）。版本 `index.md`、版本 `WORKLOG.md`、`feature/**`、工作区 `readme.md`、别的页面目录一律只读。
- 范围以任务卡为准。用户在本会话里提出超出任务卡的东西：属于本页细节的照做；会改变范围、共用定义归属、别的页面行为或统一叫法的，**不自己拍板**，写进「跨页影响」，并告诉用户这需要总控收口。
- 本页主管的实体：在本页完整定义（字段、状态机、规则）。引用的实体：只写本页触发哪些流转、遵守哪些规则，引用定义页编号，`spec.yaml → refs` 登记来源。
- 引用的定义不够用 → 上报跨页影响，不在本页另起一套。被引用的编号还不存在（主管页还没写）→ 先在本页 WORKLOG 记「等 NN 定义 X」，正文写到可写的程度，不臆造对方编号。
- 用词遵守术语表。validate 报禁用别名就改成标准叫法；确需写旧名的行加 `alias-ok`。

## 五阶段流程（不许跳步）

### 阶段 0 · 收料

- 读任务卡指向的全部材料：原型、需求池、旧文档、截图、代码、接口文档。读不了的格式（如原型源文件）让用户导出 HTML 或截图，不说「看过了」。
- 涉及已有产品时，核对本页触及的现有页面、接口、数据模型、权限、状态流转、错误处理、日志/埋点与编码约定；只查相关范围，不假装扫完全项目。
- 区分沿用项与新增/变更项。用户已明确说复用的、任务卡「已知输入」里已有的，记为已知，不再包装成新问题；能验证就补来源，暂时验证不了就注明「按用户确认复用，技术实现时核对」。
- 现有实现与用户描述冲突，或会改变既有行为、数据语义、兼容性时，指出冲突与影响，不擅自选边，列入待确认。
- 输出两栏：**已掌握的事实**（带来源）/ **缺口**。不确定的一律进缺口，不脑补。

### 阶段 1 · 杠（grill）

把用户没说出口的隐含条件问出来。维度见 [`grill-playbook.md`](grill-playbook.md)「页面用」一节，按需挑，不照单全问。

- 先复述已理解的目标、事实和约束，请用户纠正；再针对真正影响本页范围内交互、数据、权限、风险、验收的未知点追问。
- 每轮只问当前真正影响决策的问题；判断题给选项，推荐项放第一个并标「(推荐)」；不重复问已明确的事（包括任务卡里已定的）。
- 分清问题归属：产品取舍问用户；工程事实请用户提供资料或找对应技术负责人确认，不伪装成产品选择题；跨页 / 版本级的问题上报总控，不在本页拍板。
- 每轮结束更新本页 WORKLOG 的待定决策表（`D-NN-xx`，列 决策点 / 结论 / 影响面 / 状态），同时列出仍缺的事实、责任人和确认方式。
- 杠到能回答「做完后，测试拿什么数据、做什么操作、看到什么算过」为止。非阻塞问题进 `open_questions` 并写明影响和确认人；阻塞问题先等答案。
- 改动涉及存量数据时，追问存量怎么处理（对象、方式、谁提供 / 执行 / 核对、时机、怎么验证）；不得代定。答案写进相关规则即可，不单独开章节。
- 用户说「你定」时，只能代定本页的产品取舍，标「由我代定」并写依据与风险，同时列入 `open_questions`；不得代填项目现状或技术事实，也不得代定跨页事项。

### 阶段 2 · 等确认（硬门槛）

把已确认事实、沿用项、决策表和 `open_questions` 一起交给用户核对。**没拿到对本页范围和关键行为的明确确认，不写 PRD.md。**

### 阶段 3 · 产出（顺序固定）

在本页目录内：

1. **先写 `spec.yaml`**：照 `templates/spec.yaml` 与 [`spec-schema.md`](spec-schema.md)。
2. **再写 `PRD.md`**：骨架见 SKILL.md「PRD 必含内容」，细则见 [`prd-template.md`](prd-template.md)。
3. **按需画 mock**：任务卡要求，或本页布局 / 交互有新变化且文字说不清时才画；照 [`mock-spec.md`](mock-spec.md)，只画本次改动的页面与状态，并在 PRD 插锚点。纯规则、纯接口不画。
4. **生成 review.html**：`node <技能目录>/scripts/build_review.mjs <本页目录>`，禁止手写。
5. **自检**：`node <技能目录>/scripts/validate.mjs <本页目录>`，本页必须没有错误；再过一遍 SKILL.md「核心质量检查」。报出别的页面的错误时，不去改人家，记进「跨页影响」。

`<技能目录>` 为本技能 SKILL.md 所在目录。

### 阶段 4 · 收尾

- 本页 WORKLOG 只做增量更新：覆盖快照、改动变化的行（决策指向、`open_questions`、跨页影响、**未完成与依赖**）、变更记录追加一行；达到任务卡「完成标准」后标「可登记」。版本 index 和 feature 台账由总控登记，本页不改。
- **不提交、不推送。**用户在本会话说「提交」时，回复「按规矩由总控统一打包，请到总控会话说『打包』」（见 [`workspace.md`](workspace.md) 第 10 节）。
- 汇报：本页定死了哪些决策、哪些还在 `open_questions`、mock 覆盖了哪些状态、校验结果、上报了哪些跨页影响等总控收口；说清「技术拿到手第一步该干嘛」。
- 本页涉及存量数据时，在本页 WORKLOG「跨页影响」逐条报给总控（存量对象、处理方式、涉及谁、定义在哪个编号），汇报里单独点一句，由总控汇总进版本 index。
- **汇报最后必须有「未完成与依赖」一节**（每轮结束都要，不只是全部写完时），同时写进本页 WORKLOG 同名一节。没有就明确写「无」。逐条列：
  - 还没写完的部分：哪个区块 / 哪些编号是占位或待补，为什么没写完。
  - 依赖谁：依赖哪一页（或版本级 / 用户 / 技术负责人）的哪个定义、编号或答复，拿到之后本页要改哪里。例：「R-05-012 的结算单状态等 06 定义（Q-00-08），06 出来后改 R-05-012、G-05-020」。
  - 被谁依赖：已知别的页在等本页的什么，本页给了没有。
  - 阻塞程度：是否影响本页「可登记」、是否影响打包。

## 跨页影响怎么写

写在本页 WORKLOG「跨页影响」表，一条一行：

| 列 | 写什么 |
| --- | --- |
| 编号 | 本页内流水号即可（如 X-1），不占用 D/Q 编号 |
| 事项 | 需要谁改什么、为什么（如：需要 NN 的 X 实体增加某状态；某叫法建议统一为 Y） |
| 依据 | 本页编号 / 用户原话 / 材料位置 |
| 影响页 | 受影响的页面或「版本级」 |
| 状态 | 待总控 → 总控已定（写结论或 D-00 编号）→ 已同步 |

收到任务卡「待同步」的事项：改完本页、validate 通过后，在本页 WORKLOG「同步回执」记一行（哪条待同步、改了什么、日期），总控据此销项。

## 总控代改过本页时

本页 WORKLOG 会有「总控代改」记录。续作前先看一眼，以文件现状为准，别用旧上下文覆盖回去。
