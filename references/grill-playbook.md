# 杠人手册（grill playbook）

目的：让用户把「我以为你懂」的部分说出口。三条原则：

1. **判断题优先给选项**。让人选比让人写快得多，选项本身还能暴露他没想过的分支。推荐项放第一个并标「(推荐)」。
2. **按需提问**。每轮只问当前真正影响决策的问题，可能 1 个，也可能几个；不凑数，也不一次砸十几个。
3. **追问到可测**。任何答案后面接一句「那测试怎么判它过了」，答不出来就说明还没定。

---

## 零、按角色挑维度

| 角色 | 用哪些 | 问到什么程度 |
| --- | --- | --- |
| 总控 | 下表 1 目标、2 成功判定、3 范围边界、15 排期依赖；外加「总控专用」一节 | 能回答每页「做什么、不做什么、跟谁有关系」即停 |
| 页面 | 下表全部按需挑；外加第二节「容易漏的追问」 | 能回答「测试拿什么数据、做什么操作、看到什么算过」即停 |

### 总控专用

| 维度 | 典型问法 |
| --- | --- |
| 页面划分 | 这几个页面要不要一起评审 / 一起开发？分开做会不会各写一套状态？ |
| 共用实体归属 | 这个对象在哪一页被创建、在哪一页被主要修改？ |
| 跨页主链 | 从起点到终点有几步？每一步谁操作、在哪页？ |
| 统一叫法 | 同一个东西在原型 / 文档里有几种叫法？以哪个为准？ |
| 通用口径 | 有没有所有页都要守的规则（时区、精度、权限模型、审批 / 通知框架）？归哪页定义？ |
| 并行与顺序 | 哪些页必须先定？哪些可以同时开工？ |

总控不问字段、交互、异常分支；遇到了记进对应页面任务卡，交给页面去杠。

## 一、通用维度

前 8 项是多数需求绕不开的，逐项判断是否相关；不相关的跳过，别硬问。

| # | 维度 | 典型问法 |
| --- | --- | --- |
| 1 | 目标 | 这需求解决谁的什么问题？不做的话现在怎么凑合？ |
| 2 | 成功判定 | 上线后看什么现象 / 数据算成功？ |
| 3 | 范围边界 | 哪些明确不做？（这条比「做什么」更省事） |
| 4 | 角色权限 | 谁能看、谁能改、谁要审批？角色从哪来？数据按什么维度隔离？ |
| 5 | 数据字段 | 字段从哪来？必填吗？枚举给全了吗？历史数据怎么办？ |
| 6 | 状态流转 | 有哪些状态？谁能推动？驳回 / 撤回 / 作废怎么走？ |
| 7 | 异常边界 | 空态、失败、超时、重复提交、并发、权限不足，各自什么表现？ |
| 8 | 验收方式 | 测试拿什么数据、做什么操作、看到什么算过？谁验收？ |
| 9 | 通知留痕 | 什么动作要通知？通知谁、走什么渠道？操作日志记哪些字段？ |
| 10 | 外部依赖 | 依赖哪个系统 / 接口？对方不可用时怎么办？先 Mock 还是等真接口？ |
| 11 | 量级 | 数据量多大？列表多少条？有没有上限？ |
| 12 | 兼容灰度 | 老数据、老入口、老用户怎么办？要不要开关？出问题怎么回滚？ |
| 13 | 埋点 | 要观测什么？事件名、上报字段、用来回答什么问题？ |
| 14 | 文案 | 提示语谁定？有没有多语言、敏感词、合规要求？ |
| 15 | 排期依赖 | 有没有硬截止日？依赖谁先交付？ |

## 二、容易漏的追问

碰到这些情况，答案往往两个人各想各的，必须问到写死：

- **存量数据处理**：哪些老数据受影响？保留 / 映射 / 补齐 / 导入 / 清理选哪种？谁提供数据、谁执行、谁核对？上线前还是上线后？处理失败系统怎么表现？
- **规则变更后的历史数据**：按发生时刻的规则算，还是按当前规则重算？必须二选一。
- **数值口径**：精度、取整方式、单位；涉及金额时的币种、折算来源与尾差处理。
- **统计口径**：按发生时间还是入账 / 生效时间；含不含某类数据；时区是哪个。
- **归属变更**：关联关系改了以后，历史记录归属谁？
- **在途对象**：上游对象被停用 / 删除时，下游进行中的记录怎么处理？
- **列表默认值**：默认排序、默认筛选、分页大小。
- **导出**：有没有上限？超时怎么办？导出的字段和页面看到的是否一致？
- **撤回后的痕迹**：撤回 / 驳回后，附件、意见、操作日志是否保留？

## 三、杠完的标准产出：决策表

```
| 编号 | 决策点 | 结论 | 影响面 | 状态 |
| --- | --- | --- | --- | --- |
| D-01-01 | <决策点> | <结论> | <影响的页面 / 数据 / 接口> | 已定 |
| D-01-02 | <决策点> | 待定 | <影响面> | 待定 |
```

- 每条「待定」要么继续追问，要么写进 `spec.yaml → open_questions`，并标明卡住了哪条 T 编号。
- 页面决策表原样落进页面 `spec.yaml → decisions`，过程中记在本页 WORKLOG。
- 总控的版本级决策用 `00` 页号：确认后进版本 `index.md`「版本级决策」，未定的 `Q-00` 记在版本 WORKLOG。
- 用户明确确认范围和关键行为后才进入产出阶段，这是硬门槛。

## 四、反面教材

- ✗ 「请问您对这块有什么想法？」—— 开放式废话，等于把活推回去。
- ✗ 一次问十几条 —— 他会挑简单的答，难的当没看见。
- ✗ 自己填个默认值当定了 —— 用户永远不知道你替他选了什么。
- ✗ 已经说清楚的事反复确认 —— 显得谨慎，实际是浪费对方时间。
- ✗ 把「技术上怎么实现」包装成选择题问产品 —— 工程事实找技术负责人。
- ✗ 只问主流程 —— 异常分支才是研发吵架的地方。
- ✗ 总控把页面细节问一遍、页面会话再问一遍 —— 用户被问两次。总控把听到的细节记进任务卡「已知输入」，页面不再重复问。
- ✗ 页面会话替别的页面或全局拍板 —— 上报跨页影响，交总控收口。
