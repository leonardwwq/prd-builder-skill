# PRD 写法细则（标准 / 项目模式）

骨架与必含内容以 SKILL.md「PRD 必含内容」为准，写作要求与质量检查以 SKILL.md 第五、六节为准；本文件只补充各部分怎么写。用不上的部分整段不写，别留空标题。

## 头部

标题下一行引用块写元信息：`版本 · 页面（NN-页面名）· 状态 · 日期 · 关联（spec.yaml / mocks / 版本 index / 原型路径）`。项目模式页面的状态与 `spec.yaml → meta.status` 一致。

## 1 目标与范围

- 目标写现状问题 + 期望结果，能被证伪；「提升体验」不能被证伪，重写。
- 包含 / 不包含逐条列；不包含写去向（归哪页、本版不做）。
- 基于什么改、沿用什么、引用了哪些外部定义（如「反馈状态机定义见 01-<页面名>（R-01-003）」）在这里一句话交代，后文不再重复。
- 领域黑话（按需）：表 术语 | 释义，在这里落地，别指望 AI 猜。项目模式以版本 index 术语表为准，这里只补本页特有的。

## 2 场景与流程

- 涉及权限时给表：角色 | 能做什么 | 不能做什么 | 数据范围 / 权限来源。
- 核心流程表：步骤 | 操作者 | 系统行为（引用 R 编号）| 产物。跨页的步骤标明落在哪一页。流程只写顺序与分支，规则细节留给 R。

## 3 功能与规则

一个页面有多个区块（列表 / 详情 / 弹窗）时用 `### 3.1`、`### 3.2` 并列，按用户操作顺序排。每块按需包含：

**行为说明**：这块干什么、和谁联动，一到三句。

**字段**（涉及数据时）：一张表只表达字段，规则放 R。

| 字段名 | key | 类型 | 必填 | 枚举/取值 | 默认值 | 规则说明 |
| --- | --- | --- | --- | --- | --- | --- |
| <字段名> | <key> | <类型> | 是 / 否 | <取值> | <默认值> | 见 R-NN-001 |

类型写清：string(长度) / text / int / decimal(精度) / enum / date / datetime(时区) / bool / 关联对象 / 列表。数值带单位与精度（金额带币种）；时间带时区与精度。

**业务规则**：一条一个编号、一句话、能测：
- **R-NN-001** <在什么条件下，系统做什么 / 禁止什么，用户看到什么>

**状态与流转**（有状态时）：
- 本页**定义**的状态机：状态清单 + 流转表（当前状态 | 触发动作 | 操作者 | 目标状态 | 前置条件）；逆向操作（撤回 / 驳回 / 作废 / 回滚）单独写：谁能发起、有无时限、下游怎么处理。
- 本页**引用**的状态机：只写本页触发哪几条流转，注明定义所在页面，不抄状态清单。

**交互反馈与异常**：表：场景 | 触发 | 系统行为 | 用户看到。只列与本块相关的（清单见 SKILL.md 核心质量检查第 4 条）；与某条 R 重合的直接引用编号，不再展开。批量操作单独写清逐条结果与部分失败（SKILL.md「批量操作」）。

**示意**（有 mock 时）：本块末尾独占一行插锚点，格式见 [`mock-spec.md`](mock-spec.md)。

## 4 验收标准

- **G-NN-001**（验证 R-NN-001）前置：<数据准备>。操作：<步骤>。期望：<可观察结果>。
- 一条 G 验证一条或几条 R；关键规则、异常、部分失败都要被覆盖。不复述规则全文，不写「功能正常」。
- 区块多时可以按 `3.N` 分组，但都放在本章，不散回各区块。

## 5 影响与开放问题

- 影响面表：被影响对象（页面 / 数据 / 接口 / 报表 / 权限）| 影响方式 | 处理动作 | 负责人。涉及存量数据的写清处理方式与执行方（项目模式还要报给总控，见 workspace.md 第 6 节）。
- 假设：本 PRD 先按什么写、待谁确认。
- 开放问题表：编号 | 问题 | 卡谁 / 影响哪条 | 需谁回答 | 期望结论时间。有 spec 时与 `open_questions` 一致。
- 非功能与埋点（按需）：量级、导出、审计留痕；埋点：事件名 | 触发时机 | 上报字段 | 用来回答什么问题。只写有依据或经确认的数字。
- 附录（按需）：原型截图、接口样例、数据样例、术语出处。

## 要点

- **一张表只表达一件事**。字段和规则混在一张表里，AI 会漏。
- **别写「同上」「见前文」**。AI 未必读到上下文，写清编号。
- 有 spec.yaml 时：本页 R/G 编号两边都要有，PRD 里提到的本页 T/D/Q 要在 spec 里定义；引用别页编号时 validate 会去那一页核对。
- 老文档用「0 前置说明 / 1 整体概述 / 2 详细需求 / 2.N.x」结构的照旧有效，改动时不必为换骨架而重排。
