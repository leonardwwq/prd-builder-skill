# 项目模式：工作区、协作与版本规则

项目模式（多页面、跨模块、多 Agent 并行、长期维护）的**唯一权威规则**。两个角色的具体流程见 [`role-lead.md`](role-lead.md)（需求总控）与 [`role-page.md`](role-page.md)（页面 PRD）。轻量 / 标准模式不读本文件；只在已有项目工作区里改单页时，按 SKILL.md「在已有项目工作区里做单页改动」引用本文件的个别小节。

| 角色 | 管什么 | 不管什么 |
| --- | --- | --- |
| 需求总控 | 整个版本：范围、版本级决策、术语、页面划分、共用定义归属、跨页流程、任务卡、跨页影响裁决、登记、打包与交付 | 页面内部的字段、交互、异常分支、验收细节 |
| 页面 PRD | 一个页面目录：按任务卡细化到可开发 | 范围、共用定义归属、别的页面、版本级共享文件 |

## 1 工作区结构

```text
<工作区>/
├── readme.md                  # 结构说明；可写「本工作区约定」、产品级术语表
├── feature/
│   ├── index.md               # 功能清单、简介、最新涉及版本、跳转
│   └── <功能名>/
│       ├── README.md          # 功能定义；当前规格只放链接，不抄内容
│       └── versions.md        # 该功能跨版本记录，只追加
└── versions/
    └── <版本号>/
        ├── index.md           # 版本总纲（见第 8 节）
        ├── WORKLOG.md         # 总控过程日志：需求盘点、任务卡、Q-00、跨页影响裁决；不进 Git
        └── NN-<页面名>/
            ├── WORKLOG.md     # 本页过程日志；不进 Git
            ├── PRD.md         # 权威文本：人读它，AI 也读它
            ├── spec.yaml      # 机器可读：字段 / 状态 / 规则 / 验收 / 任务
            ├── review.html    # 人读版，脚本生成，禁止手写
            └── mocks/         # 按需；单文件、内联样式、零外部依赖
```

- 功能与版本是多对多，用链接互连，不用目录嵌套。
- 所有版本目录放在 `versions/` 下；版本目录下**直接**放页面目录，不加 `pages/` 等中间层。老工作区版本目录挂在根下的，总控征得用户同意后整体挪进 `versions/` 并修好相对链接；挪之前脚本照常能跑。
- 页面目录 `NN-<页面名>`：`NN` 两位页号，版本内唯一，按用户操作顺序排，由总控分配；页面名用业务叫法。
- 不单独建 `CHANGELOG.md`：版本内交付与修订记在版本 `index.md` 末尾；功能跨版本变化记在 `feature/<功能名>/versions.md`。同一件事只记一处。
- 模板：`templates/readme.md`、`feature-index.md`、`feature-README.md`、`feature-versions.md`、`version-index.md`、`WORKLOG.md`（版本）、`page-WORKLOG.md`、`spec.yaml`、`mock-skeleton.html`。用到哪个读哪个。

## 2 文件职责与写权限：一个文件只有一个写的人

| 文件 | 写什么 | 不写什么 | 谁写 | 进 Git |
| --- | --- | --- | --- | --- |
| 工作区 `readme.md` | 结构、使用方式、「本工作区约定」、可选产品级术语表 | 需求正文 | 总控 | 是 |
| `feature/index.md` | 功能名、一句话简介、最新涉及版本、跳转 | 功能细节 | 总控 | 是 |
| `feature/<功能名>/README.md` | 是什么、边界、当前状态、当前规格所在页面链接 | 状态机、字段表（只链接） | 总控 | 是 |
| `feature/<功能名>/versions.md` | 每版改了什么、涉及哪些页（只追加） | 版本内修订细节 | 总控 | 是 |
| 版本 `index.md` | 版本总纲 | 页面需求正文 | 总控 | 是 |
| 版本 `WORKLOG.md` | 总控过程与任务卡 | 正式规格、页面细节 | 总控 | **否** |
| 页面 `WORKLOG.md` | 本页过程 | 正式规格 | 该页 | **否** |
| 页面 `PRD.md` / `spec.yaml` | 本页权威需求 / 机器可读规格，本页编号在 spec 定义 | 别页定义（引用编号即可） | 该页 | 是 |
| 页面 `review.html`、`mocks/` | 脚本生成的人读版 / 本页改动涉及的状态示意 | 手写 review、未改动页面 | 该页 | 是 |

- 页面发现要改共享文件或别人的页面，写进自己 WORKLOG 的「跨页影响」，由总控裁决、下发；不自己动手。
- 唯一例外：用户明确指定时，总控可代改某一页（那页没人在做、只是同步改名等）。动手前确认没有别的会话正在改那页，改完重跑该页 build + validate，并在该页 WORKLOG 记一笔「总控代改」。
- 交付登记（页面 `meta.status` 改「已交付」、index 交付记录、feature 台账）由总控统一做；交付时页面都已停手。

## 3 编号：页号做前缀

格式 `<类型>-<页号>-<序号>`：R 业务规则（`R-01-003`）、G 验收（`G-01-002`）、T 实现任务、D 已拍板决策（`D-01-01`）、Q 开放问题。

- 页号 = 页面目录的 `NN`。页面编号只在本页 `spec.yaml` 里定义（`id:`），天然不跨页重号。
- `00` 号属于总控、表示版本级：
  - `D-00-xx`：确认后写进版本 `index.md`「版本级决策」，进 Git；页面可直接引用，validate 去 index 核对。
  - `Q-00-xx`：只记在版本 `WORKLOG.md`；页面不得引用。定了变 `D-00`，或落到页面变 `Q-NN`。
  - 不许有 `00` 号页面目录；R/G/T 没有 `00`。
- 同一页内 R/G 必须 PRD.md 与 spec.yaml 两边都有；T/D/Q 在 PRD 里提到就必须在 spec 里存在。跨页引用直接写对方编号（如「见 R-01-003」），validate 会核对。

## 4 共用定义：谁主管谁定义

多页共用的实体、状态机、规则**只定义一次**：

1. 主管页由总控指定（写在任务卡和 index「共用定义指路」）：负责创建或主要修改该实体的页面定义它（spec 的 entities / flows / rules + PRD）。
2. 其他页面只写「本页触发哪些流转 / 遵守哪些规则」，引用定义页编号，并在本页 `spec.yaml → refs` 登记；不抄状态清单。
3. 引用页觉得定义不够用（缺状态、缺字段、要改语义），上报跨页影响，由总控转给主管页改。
4. `feature/<功能名>/README.md` 不抄状态机，只链接到定义页。
5. 只有被多页平均修改、确实说不清谁主管时，总控才和用户商量单独抽出；不预设共享目录。

## 5 术语：一个东西一个叫法

- 版本 `index.md` 有「术语表」：标准叫法 | 含义 | 禁用别名（「、」分隔）。产品长期通用术语可放工作区 `readme.md` 同格式表。两处都由总控维护。
- 改名是版本级决策：记 `D-00-xx` → 术语表旧名进「禁用别名」→ 受影响页任务卡标「待同步」→ 页面改完后 validate 不再报别名。
- validate 在页面 PRD.md、spec.yaml、mocks 里扫禁用别名。确需写出旧名的行加 `alias-ok`（Markdown `<!-- alias-ok -->`，YAML 行尾 `# alias-ok`）。

## 6 存量数据：版本级一份汇总，需求负责人知情

改动动到上线前已存在的数据（改字段语义、增删必填、改状态枚举、改计算口径、改归属、换数据来源、需初始化导入等）时：

- **页面**：在相关规则里写清怎么处理，不单独开章节；每轮收尾在本页 WORKLOG「跨页影响」逐条报给总控（存量对象、处理方式、涉及谁、定义在哪个编号），汇报里单独点一句。
- **总控**：在版本 `index.md` 维护唯一一份「存量数据处理汇总」（列见第 8 节）。跨页共用的存量口径记 `D-00-xx`；必须上线前完成的同时列进版本 WORKLOG「上线检查项」。收口、打包、交付时，把新增或有变化的项单独列给用户（处理什么、谁来做、还缺什么）。
- 处理方式不得「由我代定」：产品取舍问用户，量级与执行方式问技术负责人；没定的进开放问题并写明协作方。

## 7 版本规则：版本号跟着「交付」走

| 处境 | 判定 | 改动怎么处理 |
| --- | --- | --- |
| 未交付 | 页面 `meta.status` 为 草稿 / 待评审 / 已确认 | 原地改，不新建目录、不升号；改完重跑 build + validate |
| 已交付 | `meta.status: 已交付` 且版本 index 有交付记录 | 默认冻结；用户明确要求在本版改时原地修订，总控在版本 index 末尾追加修订记录 |

- 「交付」= 文档已发给研发 / 测试 / AI 开始照着做。评审改十轮，没交付还是同一版。
- **只有用户明确说「开新版本」才建新版本目录。**版本号沿用产品自己的体系；没有体系时，加字段 / 加分支升 minor，改字段语义、删状态、接口不兼容升 major，并在版本 index 标 `[BREAKING]` 写迁移方案。
- 新版本只写本版改动到的页面，不整份复制旧页面；旧版目录不覆写。

## 8 版本 index.md（总纲）固定区块

骨架见 `templates/version-index.md`。区块标题关键字（版本级决策、术语、页面清单、共用定义、存量数据、交付与修订）别改，脚本靠它定位。

1. 版本目标与范围：为什么做、做什么、不做什么。
2. 版本级决策：编号 | 结论 | 依据 / 确认人 | 影响页面；只放已确认的 `D-00-xx`。
3. 术语表：标准叫法 | 含义 | 禁用别名。
4. 页面清单与分工：页号 | 页面 / 流程包 | 简介 | 主管实体 | 依赖 | 批次 | 负责人 | 状态 | 链接。流程包写明合并理由；版本需求清单每一项都要在这里找到归属或标「本版不做」。
5. 跨页流程总览：步骤 | 操作者 | 动作 | 所在页面。
6. 共用定义指路：实体 / 状态机 / 规则 | 定义位置 | 引用页面。
7. 存量数据处理汇总：存量对象与范围 | 处理方式 | 用户可见变化 | 提供方 | 执行方 | 核对方 | 时机 | 怎么验证 | 定义在 | 状态；没有写「本版不涉及存量数据」。
8. 交付与修订记录（只追加）：日期 | 类型 | 对象 | 内容 | 涉及页面；没交付前为空表。

## 9 WORKLOG：增量留档，可靠恢复

- 两级：版本 `WORKLOG.md` 归总控（`templates/WORKLOG.md`），页面 `NN-*/WORKLOG.md` 归该页（`templates/page-WORKLOG.md`）。只在项目模式创建。
- **不进 Git。**工作区在 Git 仓库里时用 `git check-ignore -v <路径>` 检查；没被忽略就建议 `.gitignore` 加一行 `WORKLOG.md`（匹配所有层级），用户同意后再改。validate 会检查。
- **只记增量**：顶部「快照」每轮覆盖（当前状态与版本、阶段、相关文件与依赖、下一步）；决策、开放问题、跨页影响等表只增改变化的行；「变更记录」每轮追加**一行**，不重写历史总结。
- **续作只读**：快照、未关闭的表格行、最近 3 条变更记录，以及它们指向的文件。不通读历史、不重新总结全部过程。已关闭且已落到正式文件的条目移到末尾「归档」，续作不读归档。
- WORKLOG 是过程不是结果：未确认的推测不写成决策；结论落到正式文件（版本级 → index，页面级 → PRD/spec）后只留编号指向。
- 区块名「任务卡」「跨页影响」「同步回执」「未完成与依赖」「总控代改」「上线检查项」别改，总控收口靠它们定位。
- 用户要求「先整理 / 先留档」时，只更新 WORKLOG / 底稿，不擅自生成正式 PRD。

## 10 Git：多会话共用一个仓库

多个会话共用一个工作目录和暂存区，各自零散提交会互相带走、互相顶掉。规矩：**不零散提交，由总控统一打包。**

- **页面会话一律不提交、不推送**；用户在页面会话说「提交」时，回复「按规矩由总控统一打包，请到总控会话说『打包』」。
- **只有总控提交、推送，且只在用户在总控会话明确说「打包 / 提交 / 推送」时做。**一次打包把这一轮所有会话的改动合成一个（或按页面分几个、同一次完成的）提交。
- 打包前总控必须：① 确认相关页面会话已停手（问用户），`git status` 看清要带走哪些改动，不该带的（某页写到一半）排除并告诉用户；② 汇总各页 WORKLOG「未完成与依赖」列给用户，确认后再打包；③ 跑版本级 validate，有错误先说清是哪页的、要不要排除，不带错默默提交。
- 提交用 `node <技能目录>/scripts/commit_paths.mjs -m "<说明>" -- <路径…>`（临时暂存区，不读不改共享暂存区；`--dry-run` 先看）；不要在共享暂存区先 `git add`。提交说明写清包含哪些页、哪些版本级改动。
- 推送前 `git log origin/<分支>..HEAD` 看清要推哪些提交；被拒就停下告诉用户，不擅自 rebase / stash 别人的改动。

## 11 什么时候更新什么

| 时机 | 谁 | 要动的文件 |
| --- | --- | --- |
| 开始一个新版本 | 总控 | 建版本目录、`WORKLOG.md`、`index.md` 草稿 |
| 总纲确认、分工 | 总控 | `index.md`；版本 WORKLOG 任务卡 |
| 页面开工 / 每轮结束 / 暂停 | 该页 | 本页 WORKLOG（快照 + 一行变更） |
| 页面确认后写正式规格 | 该页 | PRD.md、spec.yaml、review.html（mocks 按需） |
| 页面标「可登记」 | 总控 | index 页面清单与共用定义指路；首次出现的功能建 `feature/<功能名>/`，`feature/index.md` 加一行 |
| 页面上报跨页影响 | 总控 | 裁决后改 index（如涉及）、受影响页任务卡「待同步」、版本 WORKLOG 裁决表 |
| 用户在总控会话说「打包」 | 总控 | 按第 10 节；版本 WORKLOG 变更记录写提交号 |
| 交付 | 总控 | 各页 `meta.status: 已交付` 并重跑脚本；index 交付记录；相关 `feature/<功能名>/versions.md`；`feature/index.md` 最新版本 |
| 交付后在本版修订 | 该页改内容，总控记录 | 页面文件、重跑脚本；index 追加修订记录 |
| 用户要求开新版本 | 总控 | 新建版本目录，只放本版改动的页面 |

## 12 拆分与合并

- 默认一页一个目录；弹窗、抽屉、详情页等依附主页面的随主页面放。
- 几个页面共享同一状态机且必须一起评审 / 一起开发时，可合成流程包目录，在版本 index 写明合并理由。不要把几十页塞进一份 PRD。
- 单页 `spec.yaml` 超过约 800 行时考虑拆页或拆流程包，不在页内嵌套目录。拆页是总控的事。

## 13 常见坑

- 共用状态机在多页各抄一份 → 迟早打架。谁主管谁定义，其他页引用。
- 多个会话一起改同一个 WORKLOG / index → 互相覆盖。一个文件一个写的人。
- 存量数据处理散在各页、没人汇总 → 上线当天才发现没人准备数据。
- 改名靠口头喊话 → 总有一页漏改。进术语表，让脚本查。
- 各会话零散提交、在共享暂存区 `git add` → 互相带走、互相顶掉。
- 页面收尾只说「写完了」→ 总控不知道它还欠谁、等谁。收尾必须列「未完成与依赖」。
- 总控把每页都细化一遍 → 和页面会话撞车，还拖慢全局。总控只定到「做什么、不做什么、跟谁有关系」。
- 每轮续作把 WORKLOG 全文重读、重写总结 → 恢复成本随轮次线性增长。只读快照与未关闭项，只追加一行。
